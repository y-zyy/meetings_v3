# 처리 파이프라인 성능 분석 및 개선안

목표: **1시간 음성 최대 30건 동시 처리**를 효율적으로 수행하고, 동시 5/10/30/50/100건 x 30분/1시간/2시간
부하에서 동작을 검증한다.

## 1. 데이터 흐름

```
브라우저 ──업로드──▶ nginx ──▶ API(uvicorn x4) ──파일 저장(data/uploads)──▶ DB(meetings, status=queued)
                                     │
                                     └─ Celery chain (Redis 브로커)
   ① ingest      ffmpeg → 16kHz mono FLAC, 길이(ffprobe) 기록                  [CPU]
   ② asr         FLAC 업로드 → WhisperX /transcribe (large-v3)                [GPU]
   ③ postprocess 규칙 교정(Aho-Corasick) + LLM 오인식 교정                    [LLM]
   ④ diarize     FLAC + 교정 세그먼트 → WhisperX /align_diarize (정렬+pyannote) [GPU]
   ⑤ minutes     LLM 2-pass(초본 → 최종) 회의록                               [LLM]
   각 단계 결과는 meetings.transcript / segments / summary 에 저장, 프론트는 /status 폴링
```

1시간 회의 1건 기준 자원 사용(추정, 실서버 측정으로 보정 필요):

| 단계 | 자원 | 1시간 음성당 |
|---|---|---|
| ingest | CPU | 수 초 ~ 20초 (ffmpeg) |
| asr | GPU | RTF 0.02~0.05 → 약 1~3분 |
| postprocess | LLM | 입력/출력 각각 스크립트 전체(약 1.5~2.5만 토큰) |
| diarize | GPU | RTF 0.02~0.05 → 약 1~3분 |
| minutes | LLM | 입력 약 3만 토큰(타임스탬프·화자 포함) x 2회 + 출력 최대 4096 x 2회 |

**GPU 단계가 전체 처리량의 상한**이다. 30건 x 1시간이면 GPU 순수 작업만 약 1.5~3시간(GPU 1대, 동시성 1 기준)이다.

## 2. 발견한 문제

| # | 문제 | 영향 | 근거 |
|---|---|---|---|
| P1 | **화자 분리가 전사와 같은 `asr` FIFO 큐 사용** | 1번 회의의 화자 분리가 나머지 N-1건 전사가 끝날 때까지 밀림 → 첫 결과가 거의 마지막에야 나오고, 회의록 LLM 작업이 끝에 한꺼번에 몰림 | `celery_app.py` task_routes |
| P2 | **ASR 워커 동시성(10) ≫ GPU 동시성(1)** | 대기열이 Redis 가 아니라 HTTP 요청 안(WhisperX 세마포어)에 쌓임 → 대기 시간이 `ASR_TIMEOUT`/Celery time limit 에 포함. 타임아웃 → 재시도 시 서버는 끊긴 요청도 계속 처리하므로 **같은 오디오를 GPU 가 중복 처리** | compose `ASR_WORKER_CONCURRENCY=10`, `WHISPERX_MAX_CONCURRENCY=1` |
| P3 | **STT LLM 후처리를 스크립트 전체 1회 호출로 수행** | 30분 이상이면 출력이 `LLM_MAX_TOKENS=4096` 에서 잘려 줄 수 불일치 → **결과 전체 폐기**. LLM 시간만 쓰고 교정 효과 0. 예외도 조용히 삼킴 | `asr_postprocess.py`, 부하 테스트에서 30/30건 `줄 수 불일치(140 != 600)` 재현 |
| P4 | 외부 호출(ASR/LLM, 수 분~수십 분) 동안 DB 트랜잭션 유지 | commit 후 속성 접근으로 새 트랜잭션이 열린 채 `idle in transaction` → 동시 처리 건수만큼 커넥션 점유, VACUUM 지연 | `tasks.py` (commit 후 `meeting.file_path` 접근) |
| P5 | DB 커넥션 풀 과다 | API: uvicorn 4 x (20+40) = 최대 240 > Postgres 기본 `max_connections=100` → 부하 시 `too many clients` | `database.py` |
| P6 | `LLM_TIMEOUT=120s` | 1시간 회의록(입력 3만 토큰 + 출력 4096) 은 LLM 부하 시 120초를 넘기 쉬움 → 타임아웃 → 재시도로 LLM 부하 증폭 | `config.py` |
| P7 | 회의록 LLM 호출마다 새 OpenAI 클라이언트 생성 | 매 호출 커넥션 풀/핸드셰이크 재생성 | `llm.py` |
| P8 | 업로드 시 동기 `file.write()` 를 async 핸들러에서 수행 | 대량 동시 업로드 중 이벤트 루프 블로킹 → 같은 프로세스의 다른 요청(상태 폴링 등) 지연 | `routers/meetings.py` |
| P9 | 빈 DB 첫 기동 시 uvicorn 4프로세스가 동시에 `create_all` | `UniqueViolation` 으로 API 기동 실패(재시작으로 복구되나 첫 배포 시 장애) | `main.py`, 로컬 스택에서 재현 |
| P10 | `duration_seconds` 미기록 | 목록 화면 길이 표시 불가, 용량 산정 지표 부재 | `tasks.py` |

## 3. 적용한 개선 (브랜치 `perf/pipeline-concurrency-loadtest`)

| # | 변경 | 파일 |
|---|---|---|
| P1 | `diarize` 전용 큐 + `worker-diarize` 서비스. WhisperX 서버에 **우선순위 GPU 게이트** 도입: 정렬/화자분리(후반 단계)가 신규 전사보다 먼저 GPU 를 얻음 | `celery_app.py`, `docker-compose*.yml`, `whisperx_fastapi/main.py` |
| P2 | GPU 단계 워커 동시성을 GPU 슬롯 수(+1)로 축소 (`ASR=2`, `DIARIZE=2`) → 대기열은 Redis 에. WhisperX 는 슬롯을 얻은 뒤 **클라이언트가 끊겼으면 추론을 건너뜀**(중복 GPU 작업 방지). 오디오 디코딩은 GPU 슬롯 밖에서 수행. `/health` 에 GPU 대기열/사용시간 노출 | 동일 |
| P3 | 발화(줄) 단위 **청크(기본 2,500자) 병렬 LLM 후처리**(회의당 4병렬), 청크별 줄 수 검증·실패 시 해당 청크만 원문 유지, 프롬프트에 줄 수 명시 | `asr_postprocess.py`, `tasks.py` |
| P4 | "짧은 세션으로 읽기 → 반납 → 외부 호출 → 짧은 세션으로 저장" 패턴으로 재작성, prefork 후 엔진 dispose | `tasks.py`, `celery_app.py` |
| P5 | API 풀 `DB_POOL_SIZE=5`, `DB_MAX_OVERFLOW=10`(환경변수), Postgres `max_connections=200` | `database.py`, `config.py`, compose |
| P6 | `LLM_TIMEOUT` 기본 600초 | `config.py`, `.env.example` |
| P7 | 회의록 LLM 도 프로세스 단위 풀링 클라이언트 사용 | `llm.py` |
| P8 | 업로드 쓰기를 `asyncio.to_thread` 로 | `routers/meetings.py` |
| P9 | `create_all` 을 Postgres advisory lock 으로 직렬화 | `main.py` |
| P10 | ingest 단계에서 ffprobe 로 `duration_seconds` 기록 | `tasks.py` |

> 운영 DB `system_settings` 에 `LLM_TIMEOUT` 이 저장돼 있으면(관리자 설정 화면) 그 값이 우선한다. 관리자 설정에서 600 이상으로 맞출 것.

## 4. 30건 x 1시간 처리를 위한 권장 구성

처리 시간의 하한은 `총 GPU 작업량 / GPU 슬롯 수` 이다.

```
30건 x 1시간 x (RTF_asr + RTF_diarize) ≈ 30 x 60분 x 0.06 ≈ 108 GPU-분
  GPU 1슬롯  → 약 1시간 50분 (현재 구성)
  GPU 2슬롯  → 약 55분
  GPU 4슬롯  → 약 27분 + LLM 꼬리
```

- **GPU**: WhisperX 컨테이너를 GPU 당 1개(`WHISPERX_MAX_CONCURRENCY=1`) 띄우고 nginx `least_conn` 업스트림으로
  묶어 `ASR_API_URL` 에 지정한다. VRAM 24GB 이상이면 GPU 당 `WHISPERX_MAX_CONCURRENCY=2` 도 가능하나
  처리량 증가는 2배가 아니므로 실측 후 결정.
- **워커**: `ASR_WORKER_CONCURRENCY = GPU 슬롯 + 1`, `DIARIZE_WORKER_CONCURRENCY = GPU 슬롯`.
- **LLM**: 동시 요청 ≈ `POSTPROCESS(6) x LLM_POSTPROCESS_PARALLELISM(4) + MINUTES(10) = 34` → LLM 서버
  `max_num_seqs` 이상, 컨텍스트는 2시간 회의(회의록 2-pass 입력 약 6~7만 토큰)를 위해 **128k 권장**
  (32k 모델이면 2시간 회의록 생성 실패).

```nginx
# 예: GPU 4장, WhisperX 컨테이너 4개 앞단 로드밸런서
upstream whisperx {
    least_conn;
    server whisperx-0:9000; server whisperx-1:9000;
    server whisperx-2:9000; server whisperx-3:9000;
}
server { listen 9000; client_max_body_size 600m; proxy_read_timeout 7200s;
         location / { proxy_pass http://whisperx; proxy_request_buffering off; } }
```

## 5. 부하 테스트

방법·도구는 [`loadtest/README.md`](../loadtest/README.md) 참고.

### 5.1 테스트 환경 및 조건

- 실제 백엔드 전체(API uvicorn x4, Celery 워커, Postgres, Redis)를 기동하고, GPU/LLM 자리에 목 서버를 붙여 실행
  (`loadtest/local_stack.sh`). **실 GPU 측정이 아니므로 절대 시간은 추정치**이며, 실서버에서
  `run_loadtest.py` 로 재측정해 보정해야 한다.
- 목 서버 가정: 전사 RTF 0.03, 정렬+화자분리 RTF 0.03 (1시간 음성당 GPU 약 3.6분),
  LLM 동시 32시퀀스·디코딩 40 tok/s·prefill 4000 tok/s, `LLM_MAX_TOKENS=4096`.
- `MOCK_TIME_SCALE=0.05`(20배 압축)로 실행 후 실제 시간으로 환산. 폴링(1초) 등 압축되지 않는 지연이 함께 20배로
  환산되므로 분 단위 오차가 있다. 업로드는 16kHz FLAC(변환 생략)로 수행.
- 동시 건수 5/10/30/50/100 x 음성 30/60/120분 = 15개 시나리오, 구성별 195건.

## 6. 추가 제안 (미적용)

1. **회의록 LLM 입력 압축**: `[00:00:03 ~ 00:00:07] SPEAKER_00: ` 접두어가 줄마다 약 35자 → 입력 토큰의 30~40%.
   같은 화자 연속 발화 병합 + 시작 시각만 표기하면 prefill 비용과 2시간 회의의 컨텍스트 초과 위험이 크게 준다.
   (회의록 품질에 영향이 있을 수 있어 별도 검증 후 적용 권장)
2. **오디오 이중 전송 제거**: ASR 서버와 백엔드가 같은 스토리지를 공유하면 파일 대신 경로를 넘겨 업로드 2회(전사·화자분리)를 생략.
3. **단계별 소요 시간 영속화**: `meetings` 에 단계 시작/종료 시각(JSON) 컬럼을 두면 운영 중 병목을 상시 관측 가능.
4. **실서버 1건 기준 측정**으로 RTF/LLM 속도를 확정하고 목 서버 파라미터를 보정한 뒤 GPU 대수 최종 결정.
